Analysis done — I read every file in backend, db, cache, and the shared domain, plus the migrations and configs. The honest summary: this codebase has one endpoint that's flat-out broken by a schema rename, real authorization holes, a cache module with broken concurrency primitives, and a lot of rename-era debris. Details below, ordered by severity.

Broken outright

1. getBalances queries a column that no longer exists. db/dao/Transactions.scala:40 selects type, but V1.2.0__rename-columns.sql renamed it to op. Every call to GET /api/{wallet}/accounts that finds accounts will die with "Unknown column 'type'". This can't have been tested since the rename.
2. deleteWallet updates the wrong users' permissions. db/dao/General.scala:41 — the JSON permission cleanup runs WHERE id = $id, where $id is the wallet id matched against users.id. It should target all users whose perWallet contains the wallet. As written, it scrubs permissions of an unrelated user who happens to share the numeric id, and leaves everyone else with dangling permissions.
3. Dead server-builder expression. SftV2Server.scala:250-251: EmberServerBuilder.default[F].withHttp2 is constructed and discarded; the real builder below never gets .withHttp2. HTTP/2 is silently not enabled.
4. FullRefreshBpCache.fetchAll corrupts its own semaphore. cache/BpCache.scala:187-191: it calls refreshing.release even when tryAcquire returned false, inflating the permit count and destroying mutual exclusion. Worse, if doRefresh() throws once (DB hiccup), the permit leaks and the supervised start() loop dies silently — the currency cache then never refreshes for the life of the process.
5. Mutable scala.collection.mutable.Map inside Ref. The whole cache hierarchy (BpCache.scala:22,37,46) mutates a mutable map inside Ref.modify/update. Ref may retry the function under contention, and data.get hands the same mutable instance to concurrent readers while writers mutate it. This is undefined behavior waiting for load. Use an immutable Map.
6. Blocking unsafeRunSync inside the IO program. Main.scala:100 runs currencyCacheIO.unsafeRunSync()(runtime) inside run. The root cause is FullRefreshBpCache.apply returning the awkward Resource[IO, IO[Cache]] — it should be Resource[IO, Cache] (flatten with Resource.eval).

Security holes

7. IDOR on transactions and accounts. The wallet-scoped routes check the user's permission on the named wallet, but the underlying queries never scope the target rows to that wallet: deleteTransaction(id), deleteTransactions(ids), editTransaction, editStatus, massEditTransactions (db/dao/Transactions.scala:58-90), and deleteAccount(maId) (api/Accounts.scala:137). Anyone with rights on their own wallet can edit or delete anyone's transactions/accounts by guessing ids. Categories got this right (queries take wallet); transactions and accounts didn't. Same family: addTransaction/editTransaction don't validate that trans.account/trans.category belong to the wallet in the URL.
8. Auth cookie hygiene. AuthHelper.scala:126-131: no HttpOnly, no Secure, no SameSite → readable from JS and zero CSRF protection on cookie-authenticated mutating endpoints. Also: auth-code comparison at AuthHelper.scala:87 is non-constant-time; the code is unkeyed SHA-256 of concatenated values instead of an HMAC; logins never expire server-side and last_access is never updated or used.
9. Error leakage. The recovery wrapper (SftV2Server.scala:78-83) returns raw exception messages in 500 bodies, and processLoginFromElgoog echoes Google/JSON-decoder errors to the client.
10. Committed credentials/defaults. reference.conf ships a real-looking DB password and a login.secret placeholder that, if unchanged, makes auth cookies forgeable. The dev-assets file service (SftV2Server.scala:247) is mounted unconditionally — including in prod.

Correctness / consistency

11. Balance math is suspect. api/Accounts.scala:40-41 buckets every transaction to either start or end; enhanceAccount then computes the end balance as startAmount + end-bucket — the pre-start bucket is excluded, so "end" is not the balance at end unless the frontend re-adds the start delta. Also, the Income/Expense branches index calculatedBalances without the contains guard the Transfer branch has — a transaction in a currency not configured for its account throws and 500s.
12. Nothing is transactional. Multi-step mutations run as separate transactions: deleteWallet (traverse(_.transact)), the addWallet→permissions→cache sequence, deleteCategory's three steps, deleteAccount's shift-then-delete. editAccount (api/Accounts.scala:117-129) even runs the account UPDATE in parallel with the SELECT of currencies it then diffs against, plus three concurrent write transactions. Any partial failure leaves inconsistent data. These should compose as one ConnectionIO and transact once.
13. Crash-as-404. walletsCache.get(permalink).map(_.get) in nearly every route (SftV2Server.scala:122,128,135,…) turns an unknown permalink into a 500 NoSuchElementException instead of a 404. Same pattern: NonEmptyList(ids.head, ids.tail) on possibly-empty request bodies (api/Transactions.scala:61,77), enhanced.head / toAccount(list.head) for accounts with zero currencies, and the LocalDate query-param decoder (SftV2Server.scala:269-270) throwing (500) instead of emap-ing to a 400.

Smells

- Profanity in the code. kokot, pica, kokotPica in AuthHelper.scala:104-109 (two of the three are dead vals), and "Fuck"/"this"/"Shit" sample data in BpCache.scala:309. Also that whole Test extends IOApp object (BpCache.scala:297-347) lives in main sources and ships in the assembly jar.
- Rename debris. AccessHelper calls the wallets cache accountsCache and demands a transactor it never uses; in Main.scala:106-108 the General API is named accountsApi while the Accounts API is moneyAccountsApi. Actively misleading.
- Inconsistent environment checks. Main.scala:102 tests == "dev", SftV2Server.scala:58-66 tests == "prod" — an environment like "staging" gets dev HTML paths and dev hostname parsing but prod auth. Also hostObj.get/Port.fromInt(port).get turn config typos into bare NoSuchElementException at startup.
- MaxSizeBpCache: acquire/release pairs aren't bracketed, so any exception leaks the permit and deadlocks the cache; removeOldest calls head/tail on a possibly-empty SortedMap; emptied key-sets are never pruned from keyAges.
- Minor: UPDATE ... LIMIT 1 on a PK update (Transactions.scala:74), pointless ORDER BY date in getBalances, magic 2592000 cookie lifetime, storeLogin's error "Could not store login in DB" also masks "no such user", side-effecting config/Hikari setup at object-init in Main, unused imports (Get, Read, Currency, PureAccount in the Transactions DAO; ExecutionContext.global in Main), and blocks of commented-out code in Users.scala and BpCache.scala.

If you want my priority order for fixing: #1 and #7 first (one is a hard outage, the other is a data-access hole), then #4/#5 (cache concurrency), then the transactionality cleanup. Say the word and I'll start on any of them.
